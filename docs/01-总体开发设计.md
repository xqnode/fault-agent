# 1. 项目概述

## 1.1 项目名称

中文：

> 制造业智能故障分析 Agent

英文：

> Manufacturing Fault Analysis Agent

项目描述：

> 一个面向制造业设备运维场景的 AI Agent 系统。当工业设备发生报警时，系统自动收集设备运行数据、历史故障记录、维修工单以及设备 SOP 等多源信息，通过 LangGraph 编排分析流程，调用不同工具进行证据收集，最终生成基于证据的故障分析报告和维修建议。

---

# 2. 项目背景

在制造业场景中，设备发生异常后，通常需要由设备工程师进行人工排查。

传统排查流程：

```text
设备报警
   ↓
查看当前设备状态
   ↓
查询历史运行数据
   ↓
查看历史故障记录
   ↓
查询历史维修记录
   ↓
查阅设备维修 SOP
   ↓
人工综合判断
   ↓
制定维修方案
   ↓
创建维修工单
```

整个过程存在几个问题：

1. 数据分散在不同系统。
2. 故障排查依赖工程师经验。
3. 新工程师缺乏历史案例知识。
4. SOP 文档难以快速检索。
5. 简单故障也需要大量人工查询。

因此，本项目希望模拟：

> **给传统制造业设备运维系统增加一个 AI Agent。**

AI 不直接替代工程师做决策，而是帮助工程师：

* 自动查询数据
* 收集故障证据
* 检索维修知识
* 总结历史案例
* 提供可能原因
* 给出排查建议

最终由工程师确认。

# 5. 核心业务闭环

整个项目必须形成完整业务闭环：

```text
设备数据模拟 / 故障剧本注入
      ↓
设备运行监控
      ↓
异常检测（阈值 + 防抖）
      ↓
产生报警（含触发快照）
      ↓
AI Agent 故障分析
      ↓
多源证据收集（可追溯 Evidence）
      ↓
故障原因分析
      ↓
生成维修建议
      ↓
工程师确认 / 驳回 / 改因（HITL）
      ↓
创建维修工单
      ↓
维修执行
      ↓
工单结单（填写实际根因与措施）
      ↓
回写 fault_record + 关闭 alarm + 更新设备状态
```

这是整个项目最重要的业务主线。

所有功能必须围绕这个闭环设计。

> **关键约束**：闭环不能停在「创建工单」。结单回写后，历史案例库才会增长，下一次 Agent 检索才更接近真实运维。

## 5.1 状态联动（MVP 必做）

三套状态必须有明确转移关系，禁止前端随意改状态。

### 报警 `alarm.status`

```text
PENDING → ANALYZING → ANALYZED → RESOLVED
                ↘ FAILED（分析失败，可重跑）
```

规则：

```text
开始分析：PENDING → ANALYZING（同 alarm 仅允许一个 ACTIVE 分析）
分析成功：ANALYZING → ANALYZED
分析失败：ANALYZING → FAILED（可再次发起分析）
工单结单：ANALYZED → RESOLVED
```

### 设备 `device.status`

```text
RUNNING ↔ WARNING / FAULT
STOPPED（人工停机或维护中）
```

规则：

```text
产生 HIGH/CRITICAL 报警：RUNNING → WARNING 或 FAULT
alarm 全部 RESOLVED 且无进行中工单：恢复 RUNNING
```

### 工单 `maintenance_work_order.status`

```text
DRAFT → PENDING → PROCESSING → COMPLETED
                  ↘ CANCELLED
```

规则：

```text
工程师确认分析后创建：DRAFT / PENDING
开始维修：PENDING → PROCESSING
结单完成：PROCESSING → COMPLETED
  → 强制填写 actual_root_cause / actual_solution
  → 写入 fault_record
  → 关联 alarm → RESOLVED
  → 视情况恢复 device.status
```

例如：

```text
查询设备信息

查询传感器数据

查询历史故障

查询历史工单

```

---

## 6.3 RAG

Agent 查询：

```text
设备维修手册

设备操作规范

故障处理 SOP
```

RAG 是 Agent 的工具之一。

不是独立的 PDF 聊天机器人。

---

## 6.4 Evidence-based Analysis

这是项目最重要的设计。

Agent 的结论必须基于：

```text
实时设备数据

+

历史故障案例

+

维修知识库
```

生成分析结果。

禁止 Agent 无依据生成故障结论。

最终报告必须包含：

```text
可能原因

支持证据

建议操作
```

而不是简单说：

> 我认为设备坏了。

---

## 6.5 Human-in-the-loop

AI 不直接执行工业操作。

AI 只能：

```text
分析

↓

提出建议

↓

等待工程师确认 / 驳回 / 改因

↓

生成工单

↓

结单后沉淀真实根因
```

最终：

> 工程师确认后执行；结单结果回写系统，供后续 Agent 检索。

这更符合真实工业场景。

## 向量数据库

### MVP / 本地开发

优先推荐：

```text
PostgreSQL + pgvector
```

原因：

```text
1. 业务库已选 PostgreSQL，一套库同时存业务数据与向量
2. metadata filter（device_type 等）可用 SQL WHERE 直接做
3. Docker Compose 运维简单，面试也好讲「为什么不全库相似度乱搜」
4. 本项目 SOP 规模通常远小于百万级，pgvector 足够
```

备选（仅当想快速原型、暂不碰扩展时）：

```text
Chroma
```

但生产路径仍建议收敛到 pgvector 或独立向量库，避免后期两套检索语义不一致。

### 生产部署建议

按规模选型：

```text
默认生产（推荐本项目）：
  PostgreSQL + pgvector
  （知识库到百万级 chunk 以内、QPS 中等）

独立向量引擎（知识库变大 / 过滤与混合检索更重）：
  Qdrant
  （过滤强、运维相对轻、Agent/RAG 场景常见）

超大规模（千万～亿级向量、多集群）：
  Milvus / Zilliz Cloud
```

对本制造业故障分析 Agent：

> **生产首选 PostgreSQL + pgvector**；只有知识库与检索 QPS 明显吃紧时，再拆出 **Qdrant**。不必一上来上 Milvus。

# 17. Agent State 设计

建议：

```python
class FaultAnalysisState(TypedDict):
    """故障分析 Agent 状态"""

    alarm_id: int
    device_id: int

    # 报警信息
    alarm_info: dict

    # Agent 执行计划
    analysis_plan: list

    # 证据集合
    evidences: list

    # 工具调用记录
    tool_results: dict

    # 是否需要更多信息
    need_more_evidence: bool

    # 证据收集轮次控制（防死循环）
    evidence_round: int
    max_evidence_rounds: int  # MVP 建议 2~3

    # 分析运行状态
    analysis_status: str  # RUNNING | SUCCEEDED | FAILED
    error: str | None

    # 最终分析结果
    analysis_result: dict

    # 执行日志
    execution_logs: list
```

注意：

不要一开始把所有数据字段全部塞进 State。

State 应该负责：

> Agent 工作过程中的状态。

业务数据可以放在 Tool Result 中。

# 18. Agent 工作流程

推荐设计（MVP）：

```text
START
   ↓
Load Alarm
   ↓
Plan Analysis（合并原 Analyze Task + Create Plan）
   ↓
Collect Evidence
   ↓
Evidence Enough?
   │
   ├──── No 且 round < max ────→ Collect More Evidence
   │
   ├──── No 且 round >= max ────→ 标记 evidence_insufficient
   │
   ▼
Root Cause Analysis
   ↓
Generate Report
   ↓
END
```

说明：

```text
1. MVP 将 Analyze Task 与 Create Analysis Plan 合并为 Plan Analysis，减少一次 LLM 调用。
2. Evidence Check 必须有 max_evidence_rounds，禁止无限循环。
3. 达上限时仍生成报告，但 evidence_insufficient=true。
```

# 19. Agent 节点设计

## Node 1：Load Alarm

获取报警信息。

输入：

```text
alarm_id
```

获取：

```text
设备

报警类型

报警等级

报警时间

metric_name / measured_value / threshold_value

snapshot_json
```

并将 alarm.status 置为 `ANALYZING`。

---

## Node 2：Plan Analysis

LLM 一次性完成：

```text
判断当前故障需要哪些信息

↓

生成可执行分析计划
```

例如高温报警可能需要：

```text
设备信息

最近传感器多指标数据

历史故障

维修 SOP
```

计划示例：

```text
Step 1
查询设备基本信息

Step 2
查询最近2小时多指标变化与相关性

Step 3
查询历史相似故障

Step 4
查询设备高温处理 SOP（按 device_type 过滤）
```

---

## Node 3：Collect Evidence

Agent 根据任务调用 Tool。

例如：

```text
get_device_info

get_sensor_data

get_fault_history

search_knowledge_base
```

每轮收集后：`evidence_round += 1`。

---

## Node 4：Evidence Check

判断：

```text
当前证据是否足够？
```

路由规则：

```text
不足 且 evidence_round < max_evidence_rounds
  → 继续 Collect Evidence

不足 且 evidence_round >= max_evidence_rounds
  → 进入 Root Cause Analysis（强制结束收集）

足够
  → 进入 Root Cause Analysis
```

例如：

发现温度持续升高，但无法判断原因时，可在未达上限前继续：

```text
查询历史维修记录
```

---

## Node 5：Root Cause Analysis

LLM 根据 Evidence 进行分析。

要求：

```text
必须引用 Evidence。

禁止脱离 Evidence 猜测。
```

输出：

```text
可能原因

可能性等级

支持证据
```

例如：

```text
可能原因：

冷却系统异常

可能性：

高

支持证据：

1. 温度持续上升

2. 历史类似故障中存在冷却系统异常

3. SOP 指出高温优先检查冷却系统
```

注意：

不要输出：

```text
概率 73.28%
```

没有真实模型支持。

使用：

```text
高

中

低
```

更加合理。

---

## Node 6：Generate Report

生成最终报告。

结构化输出。

成功后：

```text
analysis_status = SUCCEEDED
alarm.status = ANALYZED
```

失败时：

```text
analysis_status = FAILED
alarm.status = FAILED
error = 原因
```

```text

Chunk

↓

Embedding + Metadata

↓

PostgreSQL + pgvector
```

### Metadata（MVP 必做）

每个 chunk 至少包含：

```text

```

检索时：

```text

Query Rewrite

Parent Document

复杂 Rerank
```

这些作为后续优化。

但：

> Metadata Filter 不属于后续优化，属于 MVP。

# 23. Evidence 证据设计

这是整个 Agent 的核心。

统一定义 Evidence（可追溯）：

建议：

```python

    "tool_name": "get_sensor_data",
    "source_id": "device:1:window:2h",
```

```text
fault_history

knowledge_base
```

`knowledge_base` 的 `raw_ref` 应能定位到：

```text
chunk_id / source_doc / page_or_section
```

前端报告中的证据应支持点击跳转到原始曲线、历史记录或 SOP 片段。

# 24. 故障分析 Prompt 原则

Agent 最终分析必须遵循：

```text
1. 只能基于提供的 Evidence 分析。

2. 如果 Evidence 不足，明确说明。

3. 不允许编造不存在的设备数据。

4. 不允许将可能原因描述为确定事实。

5. 建议必须结合 SOP 或历史案例。

6. 输出必须区分：

   观察事实

   可能原因

   建议操作
```

# 25. 最终 AI 分析报告

最终报告推荐使用结构化 JSON。


前端根据 JSON 渲染。

# 34. 项目面试核心问题

项目最终必须能够回答：

---

## 为什么使用 Agent？

因为故障分析涉及：

```text
多个数据源

不同分析步骤

动态信息查询
```

普通固定 API 无法灵活处理。

Agent 可以根据当前信息：

> 决定下一步需要查询什么。

---

## 为什么使用 LangGraph？

因为 Agent 存在：

```text
状态管理

条件分支

循环

工具调用

中断恢复
```

LangGraph 更适合这种复杂状态工作流。

---

## RAG 在项目中的作用？

RAG 不负责普通聊天。

RAG 负责：

> 为 Agent 提供设备维修专业知识。

例如：

```text
故障处理 SOP

设备维修手册
```

---

## 如何防止 AI 幻觉？

核心方案：

```text
Evidence-based Analysis
```

工程配套：

```text
1. 先收集可追溯 Evidence，再分析
2. Prompt 只允许基于 Evidence 输出
3. RAG 按 device_type 过滤，避免串文档当证据
4. 证据不足时 evidence_insufficient=true，不假装确定
5. 工程师 HITL 确认后才创建工单
6. 结单实际根因回写，持续校正案例库
```

如果证据不足：

```text
明确说明无法确定。
```

---

## 为什么不让 LLM 直接查询数据库？

原因：

```text
安全性

SQL 幻觉

数据权限

业务逻辑
```

Agent 通过 Tool：

```text
Agent

↓

Tool

↓

Service

↓

Database
```

Tool 控制数据访问范围。

---

## 为什么不做 Multi-Agent？

第一版：

```text
单 Agent
```

已经可以完成：

```text
任务规划

工具调用

证据收集

分析
```

Multi-Agent 会增加：

```text
复杂度

Token 消耗

调试难度
```

因此优先保证单 Agent 的质量。

# 35. 最终项目介绍

面试时：

> 我做的是一个制造业智能故障分析 Agent，项目主要模拟制造业设备发生异常后的故障分析场景。
>
> 传统设备发生报警后，工程师通常需要手动查询设备运行数据、历史故障记录以及设备维修 SOP，再结合经验进行故障排查。
>
> 所以我使用 FastAPI 搭建工业设备运维系统，并使用 LangGraph 构建故障分析 Agent。当设备发生报警后，Agent 会根据报警类型制定分析计划，调用 Tool 查询设备数据、历史故障和维修工单，同时通过带设备类型过滤的 RAG 检索维修知识库。
>
> 在收集多源信息后，我将这些信息统一组织为可追溯 Evidence，要求 LLM 只能基于 Evidence 进行根因分析，并限制证据收集轮次避免死循环。最终输出观察结果、可能原因、支持证据以及维修建议，经工程师确认后创建工单；结单时回写真实根因，形成案例沉淀闭环。
>
> 整个项目的核心不是做一个聊天机器人，而是探索如何将 LLM 和 Agent 能力嵌入传统制造业运维流程，让 AI 帮助工程师完成信息检索、故障分析和辅助决策。

# 36. 项目开发原则

开发过程中严格遵守：

### 原则 1

先完成业务。

再加入 AI。

---

### 原则 2

不要为了技术而使用技术。

例如：

```text
需要查询 SOP

↓

使用 RAG
```

而不是：

```text
为了使用 RAG

↓

强行增加 PDF 问答
```

---

### 原则 3

MVP 优先。

不要一开始：

```text
Multi-Agent

MCP

Redis

复杂 RAG

Kubernetes
```

但 MVP 该做的工程约束（状态机、幂等、证据上限、metadata filter、结单回写）不能省。

---

### 原则 4

Agent 必须服务业务。

不要做：

```text
万能 AI 助手
```

只做：

> 工业故障分析。

---

### 原则 5

所有 AI 结论必须有 Evidence。

这是项目最重要的设计原则。

---

### 原则 6

演示必须可复现。

```text
故障剧本 + seed_demo + MOCK_LLM
```

面试现场不能依赖“碰运气出报警”或外网 LLM 必通。
