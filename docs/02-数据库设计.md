## 1. 设计原则

1. 业务数据与向量数据统一落在 PostgreSQL，降低运维复杂度。
2. 报警必须保存触发快照，支持事后追溯。
3. 工单结单必须回写 `fault_record`，形成案例沉淀闭环。
4. 同一报警同一时刻仅允许一条进行中的 Agent 分析（幂等）。
5. 枚举状态由后端状态机控制，禁止前端随意改库。

---

## 2. ER 关系

```text
device 1 ──────── N device_sensor_data
device 1 ──────── N alarm
device 1 ──────── N fault_record
device 1 ──────── N maintenance_work_order

device_type / device ── N device_threshold

alarm 1 ── N agent_analysis（历史可多条；同一时刻 RUNNING 至多 1 条）
alarm 1 ── 0..N maintenance_work_order
agent_analysis 1 ── 0..1 maintenance_work_order

maintenance_work_order COMPLETED
        ↓
   写入 fault_record
        ↓
   alarm.status = RESOLVED
```

知识库：

```text
knowledge_document 1 ── N knowledge_chunk（含 embedding vector）
```

## 3. 状态机

### 3.1 设备 `device.status`

| 状态 | 含义 |
|------|------|
| `RUNNING` | 正常运行 |
| `WARNING` | 告警中 |
| `FAULT` | 故障 |
| `STOPPED` | 停机 / 维护 |

规则：

- 产生 `HIGH` / `CRITICAL` 报警：`RUNNING → WARNING` 或 `FAULT`
- 关联 alarm 全部 `RESOLVED` 且无进行中工单：恢复 `RUNNING`

### 3.2 报警 `alarm.status`

```text
PENDING → ANALYZING → ANALYZED → RESOLVED
                ↘ FAILED（可重跑）
```

| 转移 | 触发 |
|------|------|
| `PENDING → ANALYZING` | 开始 AI 分析 |
| `ANALYZING → ANALYZED` | 分析成功 |
| `ANALYZING → FAILED` | 分析失败 |
| `ANALYZED → RESOLVED` | 工单结单 |
| `FAILED → ANALYZING` | 重新分析 |

### 3.3 工单 `maintenance_work_order.status`

```text
DRAFT → PENDING → PROCESSING → COMPLETED
                 ↘ CANCELLED
```

| 转移 | 触发 |
|------|------|
| 创建 | 工程师 HITL 确认分析后 |
| `PENDING → PROCESSING` | 开始维修 |
| `PROCESSING → COMPLETED` | 结单（强制填实际根因/措施） |

结单副作用：

1. 写入 `fault_record`
2. 关联 `alarm → RESOLVED`
3. 视情况恢复 `device.status`

### 3.4 分析 `agent_analysis.status`

| 状态 | 含义 |
|------|------|
| `RUNNING` | 执行中 |
| `SUCCEEDED` | 成功 |
| `FAILED` | 失败 |

幂等：

- 同一 `alarm_id` 仅允许一条 `RUNNING`
- 重复创建分析：返回已有 `analysis_id`
- 仅 `FAILED` 允许重新发起

## 4. 表结构

### 4.1 `device` 设备

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT IDENTITY | PK | 主键（`GENERATED ALWAYS AS IDENTITY`） |
| device_code | VARCHAR(64) | UNIQUE NOT NULL | 设备编号，如 SMT-001 |
| device_name | VARCHAR(128) | NOT NULL | 设备名称 |
| device_type | VARCHAR(32) | NOT NULL | SMT / REFLOW / ROBOT / ASSEMBLY |
| location | VARCHAR(128) | | 位置 |
| status | VARCHAR(32) | NOT NULL | 见状态机 |
| created_at | TIMESTAMPTZ | NOT NULL | 创建时间 |
| updated_at | TIMESTAMPTZ | NOT NULL | 更新时间 |

索引建议：

- `UNIQUE(device_code)`
- `INDEX(device_type)`
- `INDEX(status)`

---

### 4.2 `device_threshold` 阈值

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT IDENTITY | PK | 主键（`GENERATED ALWAYS AS IDENTITY`） |
| device_type | VARCHAR(32) | | MVP 优先按机型配置 |
| device_id | BIGINT | FK nullable | 可选：单设备覆盖 |
| metric_name | VARCHAR(64) | NOT NULL | temperature / pressure / vibration / power |
| warning_max | NUMERIC(12,4) | | 预警上限 |
| alarm_max | NUMERIC(12,4) | NOT NULL | 报警上限 |
| unit | VARCHAR(16) | | 单位，如 ℃ |
| created_at | TIMESTAMPTZ | NOT NULL | |

约束建议：

- `CHECK (device_type IS NOT NULL OR device_id IS NOT NULL)`
- `UNIQUE(device_type, metric_name)`（按机型配置时）

示例：

```text
device_type=SMT, metric_name=temperature, warning_max=85, alarm_max=90, unit=℃
```

禁止全厂硬编码 `temperature > 90`。

---

### 4.3 `device_sensor_data` 传感器数据

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT IDENTITY | PK | 主键（`GENERATED ALWAYS AS IDENTITY`） |
| device_id | BIGINT | FK NOT NULL | 设备 |
| temperature | NUMERIC(12,4) | | 温度 |
| pressure | NUMERIC(12,4) | | 压力 |
| vibration | NUMERIC(12,4) | | 振动 |
| power | NUMERIC(12,4) | | 功率 |
| record_time | TIMESTAMPTZ | NOT NULL | 采样时间 |

索引建议：

- `INDEX(device_id, record_time DESC)`

保留策略（MVP）：

- 采样周期：10~30 秒
- 保留最近 7 天（或定期清理）

---

### 4.4 `alarm` 报警

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT IDENTITY | PK | 主键（`GENERATED ALWAYS AS IDENTITY`） |
| device_id | BIGINT | FK NOT NULL | 设备 |
| alarm_type | VARCHAR(64) | NOT NULL | 如 TEMPERATURE_HIGH |
| alarm_level | VARCHAR(16) | NOT NULL | LOW/MEDIUM/HIGH/CRITICAL |
| alarm_message | TEXT | | 描述 |
| metric_name | VARCHAR(64) | NOT NULL | 触发指标 |
| measured_value | NUMERIC(12,4) | NOT NULL | 触发实测值 |
| threshold_value | NUMERIC(12,4) | NOT NULL | 触发时阈值 |
| snapshot_json | JSONB | NOT NULL | 多指标快照 |
| status | VARCHAR(32) | NOT NULL | 见状态机 |
| created_at | TIMESTAMPTZ | NOT NULL | 产生时间 |
| resolved_at | TIMESTAMPTZ | | 关闭时间 |

`snapshot_json` 示例：

```json
{
  "temperature": 98,
  "pressure": 1.2,
  "vibration": 0.4,
  "power": 3.1
}
```

防抖规则（业务层）：

- 同一指标连续 N 次（建议 N=3）超过 `alarm_max` 才产生报警

索引建议：

- `INDEX(device_id, created_at DESC)`
- `INDEX(status)`
- `INDEX(alarm_type)`

### 4.5 `agent_analysis` AI 分析结果

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT IDENTITY | PK | 主键（`GENERATED ALWAYS AS IDENTITY`） |
| alarm_id | BIGINT | FK NOT NULL | 报警 |
| status | VARCHAR(32) | NOT NULL | RUNNING/SUCCEEDED/FAILED |
| analysis_result | JSONB | | 结构化报告 |
| execution_trace | JSONB | | 节点/工具执行轨迹 |
| evidence_list | JSONB | | 可追溯证据列表 |
| engineer_decision | VARCHAR(32) | | APPROVED/REJECTED/EDITED/null |
| selected_cause | TEXT | | 工程师确认/修改后的原因 |
| edit_recommendations | JSONB | | 修改后的建议列表 |
| feedback_note | TEXT | | 工程师备注 |
| error_message | TEXT | | 失败原因 |
| created_at | TIMESTAMPTZ | NOT NULL | |
| updated_at | TIMESTAMPTZ | NOT NULL | |

`analysis_result` 建议结构：

```json
{
  "summary": "...",
  "observations": ["..."],
  "possible_causes": [
    {
      "cause": "冷却系统异常",
      "likelihood": "HIGH",
      "evidence": ["..."]
    }
  ],
  "recommendations": ["..."],
  "evidence_insufficient": false
}
```

Evidence 建议结构：

```json
{
  "source_type": "sensor_data",
  "source_name": "设备传感器数据",
  "tool_name": "get_sensor_data",
  "source_id": "device:1:window:2h",
```

部分唯一索引建议（幂等）：

```sql

ON agent_analysis (alarm_id)
WHERE status = 'RUNNING';
```

### 4.8 `knowledge_document` / `knowledge_chunk`（RAG）

#### `knowledge_document`

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGSERIAL | PK | |
| title | VARCHAR(256) | NOT NULL | 文档标题 |
| source_doc | VARCHAR(512) | NOT NULL | 来源路径/文件名 |
| doc_type | VARCHAR(64) | NOT NULL | SOP / MANUAL / GUIDE |

#### `knowledge_chunk`

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGSERIAL | PK | |
| document_id | BIGINT | FK NOT NULL | 所属文档 |
| chunk_index | INT | NOT NULL | 分块序号 |
| content | TEXT | NOT NULL | 文本 |

检索约束：

生产说明：

- 本项目默认 **PostgreSQL + pgvector**
- 知识库规模显著增大后再评估拆出 Qdrant

## 5. 结单事务（必须原子）

`POST /api/work-orders/{id}/complete` 在同一事务内完成：

1. 校验工单状态为 `PROCESSING`
2. 写入 `actual_root_cause` / `actual_solution`，状态改为 `COMPLETED`
3. 插入 `fault_record`
4. 更新关联 `alarm.status = RESOLVED`，写 `resolved_at`
5. 若该设备无未关闭报警且无进行中工单，恢复 `device.status = RUNNING`

任一步失败则整体回滚。

## 6. 种子数据要求

文件：`seeds/seed_demo.sql`

至少包含：

- 设备 `SMT-001`
- SMT 温度阈值
- 若干历史 `fault_record`
- SOP 文档及 chunk（可先文本，embedding 由 ingest 任务生成）
- 可通过剧本稳定生成的黄金报警路径

配合：

```text
MOCK_LLM=1
```

保证无外部 LLM 时也可演示完整闭环。

## 7. 扩展约定

1. 金额/高精度数值统一用 `NUMERIC`，时间统一 `TIMESTAMPTZ`。
2. JSON 字段用 `JSONB`，便于查询与索引。
3. 软删除 MVP 不做；删除仅限后台运维脚本。
4. 用户权限 / 多租户 MVP 不做，表结构预留即可，不提前实现。
